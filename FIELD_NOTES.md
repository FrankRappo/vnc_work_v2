# vnc_work_v2 — полевые заметки (обкатка вживую 2026-07-16)

Проверено на живой AnyDesk-сессии к удалённой Windows-машине. Итог: три механизма v2 рабочие,
плюс два НЕ-очевидных полевых открытия (фокус клавиатуры и калибровка haiku) и один баг-фикс.

## Три механизма (все проверены вживую)
1. **template-match** (`rc.sh find` / `click-template`, движок `vmatch.py`) — детерминированно,
   БЕЗ LLM, токенов на «зрение» НОЛЬ. Даёт точный центр эталона + score; ниже порога — репорт
   промаха, а не дикий клик. Для повторяющихся элементов (Пуск, диалоги) — основной путь.
   Вживую: Пуск найден score 1.0 в (161,1037), клик открыл меню.
2. **haiku-глаз (откалиброван)** (`rc.sh crop --grid` + haiku + `deproject`) — для НОВЫХ элементов
   без эталона. После калибровки (ниже) даёт ±1px.
3. **verify-after-click + retry** (`vmatch verify`) — сравнивает регион до/после; `changed:false`
   = клик не дошёл → re-locate + retry. Вживую ловил недошедший клик (AnyDesk иногда глотает).

## Полевое открытие 1 — КЛАВИАТУРА требует РЕАЛЬНОГО КЛИКА для фокуса (критично)
Симптом: клики по удалённой долетают, а клавиатура (`xdotool type/key`) — НЕТ (Win-клавиша не
открывала Пуск, ввод в поля не появлялся). Казалось «AnyDesk не отдаёт клавиатуру».
Причина: окну AnyDesk-сессии на :99 нужен РЕАЛЬНЫЙ КЛИК для клавиатурного фокуса.
`xdotool windowactivate <wid>` фокус ВВОДА не даёт (fluxbox) — клавиши уходят в никуда.
Фикс: ПЕРЕД любой печатью сделать реальный клик В ОКНО сессии (клик по цели через
template-match заодно и фокусит). После этого `xdotool type`/`key`/`super`/`ctrl+v` долетают.
Проверено: после клика-фокуса `xdotool key super` открыл Пуск на удалённой.
Вывод для драйвера: **клик (template) → окно в фокусе → печать**. Не полагаться на windowactivate.

## Полевое открытие 2 — КАЛИБРОВКА haiku-глаза
Симптом: на ШИРОКОМ кропе (весь низ экрана, ~20 линий сетки) haiku называл координату мимо
на сотни px (Пуск на ~160 читал как 500 — брал не ту линию).
Калибровка (что починило):
- УЗКИЙ кроп вокруг ожидаемой цели (мало линий = нельзя спутать), НЕ широкий;
- МЕЛКАЯ сетка (`--step 25`) + подписи с чёрной халообводкой (читаемы на любом фоне) —
  сделано в `stamp_grid` (veye.py): подписи сверху И снизу линий, обводка halo;
- промпт: «между какими двумя ПОДПИСАННЫМИ линиями центр» — haiku читает значение ПО ЛИНЕЙКЕ.
Результат: haiku прочитал Пуск (162,1037) при истине (161,1037) — ±1px (было мимо на 340px).
Остаточные ±1-2px = глазомерная интерполяция между линиями; для клика (кнопка ~30px) не важно.
Нужен пиксель-в-пиксель — бери template-match.

Рецепт вызова (пример):
```
python3 lib/veye.py crop --scene <кадр> --out screens/cal --region <x,y,w,h> --scale 6 --step 25 --grid --json
# → haiku читает screens/cal.png, называет real X,Y по подписям; deproject не нужен (подписи=реальные px)
```

## Полевое открытие 3 — КИРИЛЛИЦА вводится ТОЛЬКО через БУФЕР ОБМЕНА, не keystroke (T48, 2026-07-23)
Симптом (стопор T47): `xdotool type` кириллицы через RustDesk-вьювер = 1 символ/мусор — вьювер
шлёт keysym'ы/keycodes, которые раскладка удалённой Windows не мапит. Русский текст не доходит.
Фикс (проверен вживую против DESKTOP-VGVHEOU, 1С-сервер, через RustDesk):
  1. поставить ЛОКАЛЬНЫЙ X-буфер: `printf '%s' "$T" | xclip -selection clipboard` — полный UTF-8 цел;
  2. дать вьюверу СИНХРонизировать буфер на удалёнку (нужен КЛИК-фокус в окно вьювера + пауза ~0.7с);
  3. `xdotool key ctrl+v` — обычный ASCII-хоткей, вьювер его форвардит верно.
Доказано: 55-символьная кириллица («Проверка_Кириллица…_ЖилетСигнальный») вставилась ЦЕЛИКОМ в
удалённое поле, без мойбейка (readback haiku по кропу; OCR-огрехи ≠ ошибки вставки).
Инструмент: **`clip_paste.sh`** (DRY-RUN без `RC_LIVE=1`): авто-поиск окна вьювера (по площади —
крупнейшее из «Remote Desktop|RustDesk|AnyDesk»; `xdotool --name` НЕ умеет `|`-альтернацию с
пробелами → перебираем паттерны), клик-фокус в целевое поле, set-clip, пауза-синк, Ctrl+V.
Флаги: `--replace` (Ctrl+A до вставки = перезапись поля), `--enter`, `--set-only`.
Гоча: перед вводом в поле — РЕАЛЬНЫЙ клик по полю (даёт и фокус клавы, и фокус поля).

## Полевое открытие 5 — скриншот УДАЛЁННОЙ машины лучше снимать НА НЕЙ САМОЙ (T67)
`srvshot/srvshot.sh` — снимок экрана через SSH средствами самой машины (.NET `CopyFromScreen`),
без вьювера вообще. Плюсы: не зависит от живости RustDesk (см. открытие 4), нет хрома вьювера в

`schtasks /ru <user> /it` (интерактивный токен, сессия 1) — так сделано в `shot_run.ps1`.
Гоча-2: сам bat-лаунчер показывает окно `cmd.exe` ПОВЕРХ цели и портит кадр. Нужное окно поднимать
на передний план программно (`EnumWindows` + `SetForegroundWindow` по подстроке заголовка), затем
снимать; заголовки окон заодно бесплатно отвечают «а открылось ли вообще».

## Полевое открытие 7 — кабинет (Vaadin/SPA) водится ДОВЕРЕННЫМ вводом, а данные брать из СЕТИ (T71, 2026-07-25)
Задача: достать из ЛК ОФД карточку конкретного чека (марочная позиция, ошибки ФД). Прошли три
ложных вывода подряд — каждый чинится одним механизмом:
1. «Клик по строке грида не доходит» — на самом деле `el.click()` (untrusted) грид игнорирует.
   Фикс: `CDP_CLICK="x,y"` → `Input.dispatchMouseEvent` (см. `cdp/README.md` гоча 8).
   Проверка попадания без картинки: `document.elementFromPoint(x,y)` + `grid.activeItem`.
2. «Двойной клик не работает» — одно событие с `clickCount:2` не даёт `dblclick`; нужны ДВЕ пары
   press/release (1, затем 2). Карточка ЛК ОФД-Я открывается именно по ДВОЙНОМУ клику.
3. «Ничего не открылось» — модалка была `<iframe>`, а `document.body.innerText` содержимое
   iframe НЕ включает. Дамп `outerHTML` + греп показал `<iframe src="VAADIN/dynamic/resource/...">`.
   Читать: `CDP_FRAME=<подстрока URL>` (Runtime.evaluate в main world фрейма — видны его
   JS-переменные `ext_json`/`cname`, т.е. РАЗОБРАННЫЙ сервером документ, а не вёрстка).
Плюс `cdpnet.sh` (CDP Network domain): показывает, ЧТО сервер ответил на действие. Пустой UIDL
(`for(;;);[{"syncId":N,"clientId":N}]` без `execute`) = «клик дошёл, делать нечего» — это отличает
недошедший клик от отключённого пункта меню (у нас так вскрылось, что раздел «Уведомления о КМ»
у аккаунта `disabled`, а не «не кликается»).
Экономика: ноль скриншотов и ноль токенов на зрение — весь разбор по тексту/JSON.

## Полевое открытие 8 — вход в кабинет по ЭЦП делается ПОДПИСЬЮ, а не браузерным плагином (T72, 2026-07-25)
Задача: попасть в ЛК Честного знака (вход только «Войти с электронной подписью») и прочитать карточку
выбытия кода. Плагин `КриптоПро ЭЦП Browser plug-in` живёт в ПРОФИЛЕ владельца, а его Chrome запущен
(профиль под эксклюзивной блокировкой) — казалось, что без владельца никак. Оказалось, плагин не нужен.

**Вход = один HTTP-раунд с подписью, из PowerShell:**
```
GET  /api/v3/auth/cert/key                 -> {uuid, data}          (или /api/v3/true-api/auth/key)
     подписать data
POST /api/v3/auth/cert/  {uuid, data:<b64>} -> {token}   (True API: /api/v3/true-api/auth/simpleSignIn)
```
🔴 Гоча, которая стоила 4 круга: подпись должна быть **ПРИСОЕДИНЁННАЯ (attached)** над UTF-8-байтами
строки `data`. Открепленная (как читается в методичках) отвергается: `403 {"error_message":"Подпись
невалидна. Код ошибки: 2"}`. Матрица, которую пришлось прогнать (все detached → 403): UTF-8, UTF-16LE,
base64(data), hex-decoded. Прошла только attached/UTF-8.
Подписывать — штатным .NET, CryptoPro CSP подхватывается через CAPI:
`SignedCms(ContentInfo, detached=false)` + `CmsSigner(cert)` с `DigestAlgorithm = 1.2.643.7.1.1.2.2`
(ГОСТ Р 34.11-2012 256), `ComputeSignature($signer, $true)` — **silent=true работает, PIN не спрашивается**;
`signingCertificateV2` (1.2.840.113549.1.9.16.2.47) .NET добавляет сам, т.е. это уже CAdES-BES.
`CAdESCOM.Store.Open(...)` из PowerShell падает `NullReferenceException` (COM-биндер) — в CAdESCOM лезть
не нужно вообще.

**Архитектура кабинета ЦРПТ (важно для навигации):** `markirovka.crpt.ru` = ЕЛК-оболочка;
данные по товарной группе — на ОТДЕЛЬНОМ хосте `<группа>.crpt.ru` (вода → `water.crpt.ru`).
Токен = СЫРОЙ JWT в `localStorage['token']`; между поддоменами шарится КУКАМИ на `domain=.crpt.ru`:
`count`, `tokenPart<N>` (нарезка по 4000 симв.), `tokenType=Bearer`, `tokenStorageLocation=cookie`.
Выставить их из JS + положить `localStorage['token']` = полноценный вход в кабинет группы (проверено:
шапка «ЧЕПРАСОВ В. В.», меню Коды/Склад/Документы/Чеки).
- 🔴 `/api/v3/facade/*` отдаёт `403 nginx` ВСЕМ и ВСЕГДА (и из PowerShell, и из same-origin fetch
  настоящего браузера, и с токеном, и с куками) — мёртвый префикс из старого бандла. Не тратить круги.
  Живой API кабинета — `/bff-elk/...`, и он спокойно принимает `Authorization: Bearer` из ЛЮБОГО клиента.
  То есть: браузер нужен ровно чтобы УЗНАТЬ имена ручек (`cdpnet.sh`), дальше — обычный HTTP.
- Роуты у кабинетов РАЗНЫЕ: у воды Документы = `/requests/list` (а не `/documents/list` — тот даёт
  «СТРАНИЦА НЕ НАЙДЕНА»), Чеки = `/receipt/list`, Коды = `/cis/list`.
- Фильтр `POST /bff-elk/v1/cis-history/list` требует `{"cis":["<КИ>"]}` — СПИСОК. Строкой →
  `400 Failed to read HTTP message`, а вложенным `{"filter":{"cis":...}}` → `400 «Должен быть заполнен
  параметр cis»`. Два разных 400 на одну ошибку — не путать.
- Выбытие через ККТ — НЕ документ: в `doc/list` / «Документы» его нет вообще, он лежит в реестре
  «Чеки» (`POST /bff-elk/v2/receipts/search`) как «Чек на реализацию», а история кода ссылается на него
  по `docId`. Искать его среди документов = гарантированный ложный вывод «документа нет».

## Инструмент: `rps.sh` / `rps_run.ps1` — PowerShell на удалённой машине с UTF-8 наверх (T72)
`bash rps.sh probe.ps1 /tmp/out.txt` — залить скрипт, выполнить, забрать вывод ТЕКСТОМ в UTF-8.
Зачем отдельный хелпер, а не `ofd_ssh.sh 'powershell -Command ...'`:
1. stdout OpenSSH идёт через кодовую страницу консоли (cp866) → кириллица в мойбейк, гpepы мимо;
2. командную строку ssh СНАЧАЛА разбирает `cmd.exe`, поэтому `*>&1` в `-Command` съедается как
   cmd-редирект (получаешь синтаксическую ошибку PowerShell и отлаживаешь не то);
3. PS 5.1 читает файл без BOM как ANSI → кириллические литералы в скрипте ломаются (rps.sh дописывает BOM).
Раннер стримит вывод (`Out-String -Stream`) — то, что напечаталось ДО падающей строки, доходит
(буферизация через один `Out-String` теряла всё и проба читалась как «ничего не работает»).

## Гочи PowerShell, которые стоили кругов (T72)
1. 🔴 **Имена переменных в PowerShell РЕГИСТРОНЕЗАВИСИМЫ.** `$h` и `$H`, `$b` и `$B` — ОДНА переменная.
   `$H='https://…'` затем `$h = ... | ConvertFrom-Json` молча убивает базовый URL, и получаешь
   `Недопустимый URI: Невозможно определить формат URI` в месте, где всё «очевидно правильно».
2. `Try` — зарезервированное слово: функция с таким именем даёт «В операторе Try отсутствует блок операторов».
3. `МояФункция ... | Out-Null` глотает и печать функции тоже → файл вывода на 0 байт («ничего не вернулось»).
4. Per-object `$_ | Out-String` в конвейере после `Format-Table` падает `NullReferenceException`
   (Format-Table подмешивает null-элементы) — использовать `Out-String -Stream` на весь поток.
5. 🔴 **Маскировать секреты ДО обрезки.** `substring(0,200)` обрубает `"token":"…"` и regex-маска
   перестаёт совпадать → в лог уезжает начало живого JWT. Сначала mask, потом truncate.

## Полевое открытие 9 — `kso-anydesk-stale-frame`: кадр от 31 июля прочитан как «сейчас» (T175, 2026-08-05)

Симптом: снял кадр экрана AnyDesk, взял файл из каталога инструмента по маске
(`ls -t .../ad97/*.png | head -1`) — на картинке живая сессия к КСО №3 с открытым PowerShell.
Вывод «мой ввод ушёл на боевую кассу» оказался ЛОЖНЫМ: файл `full.png` лежал там **с 31 июля**,
а в свежем кадре только главное окно AnyDesk.

Причина — каноничная (и повторённая в шести драйверах) форма съёмки:

```bash
scrot -o "$S/$L.png" 2>/dev/null && convert "$S/$L.png" ... "$S/$L.jpg" && echo "$S/$L.jpg"
```

Три дефекта сразу: (1) при неудаче она МОЛЧИТ (`2>/dev/null` + `&&`); (2) прошлые `$L.png/$L.jpg`
ОСТАЮТСЯ лежать — «кадр» по этому пути всё равно есть; (3) в выводе нет ВРЕМЕНИ съёмки, а по
картинке июльская от сегодняшней не отличается.

Почему съёмка вообще молча падает (проверено 05.08 воспроизведением):
* дисплей не поднят / поднят ДРУГОЙ (`AD_SCREENS`/`RC_SCREENS` задали при `up` и забыли при `shot`
  — кадры разъезжаются по двум каталогам, и в «другом» лежит залежь);
* 🔴 **`scrot` не может перезаписать существующий файл, если тот принадлежит ДРУГОМУ пользователю**
  (`scrot: Saving to file … failed`, код 1). В общих каталогах `.jpg` часто root-овские, а `.png`
  свои — тогда `.png` свежий, а `.jpg`, который обычно и читают, прошлый. Тот же механизм уже
  ловили в T138 (31.07): «часть кадров читалась свежей, будучи трёхмесячной».

Опаснее обычной ошибки: устаревший кадр не выглядит сломанным. Это правдоподобная картинка, по
которой принимают решения и **кликают по координатам на живой кассе**.

Что сделано (T175): общий `shotlib.sh` в `/work/vnc_work_v2-vm121-review` + правки во всех «глазах». Контракт
съёмки теперь такой:
1. артефакты лейбла сносятся ДО съёмки — унаследовать нечего;
2. провал = `SHOT_FAIL` в stderr и код возврата 1 (в т.ч. «scrot вернул 0, но файл пуст»);
3. на успехе печатается ВРЕМЯ съёмки и DISPLAY, путь — ПОСЛЕДНЯЯ строка (`| tail -1` не ломается);
4. `where` — какой DISPLAY и какой каталог кадров использует ЭТОТ запуск;
5. `clean [сут]` — залежь в `attic/<ts>/` (не удаляет), эталоны `*tmpl*`/`*template*` и маски из
   `<screens>/.keepframes` остаются на месте: им положено быть старыми;
6. `rc.sh`: НЕЯВНО выбранная сцена (`ls -t | head -1`) старше `RC_SCENE_MAX_MIN` (30 мин) —
   `find/crop/grid/ocr/classify` отказываются по ней рассуждать; явно названную сцену уважают, но
   печатают её возраст. Снять: `RC_SCENE_MAX_MIN=0`.
7. `shot1.sh`/`srvshot.sh` (кадр едет с ЧУЖОЙ машины) проверяют возраст кадра ПО ЧАСАМ ТОЙ машины
   и не тянут его, если он там не обновился.

Родственные грабли, из той же семьи «картинка врёт»: открытие 4 (`classify: live` на замороженном
кадре) и 29.07 — RustDesk рисует мимо X-фреймбуфера, `scrot` отдаёт пустой рабочий стол при живой
сессии. Общее правило: **свежесть кадра доказывается временем и кодом возврата, а не тем, что
файл существует и на нём что-то похожее.**

## `ps-alias-H-get-history` — не называть функции одной буквой в PowerShell (06.08.2026)

**Симптом.** Скрипт падает не с «функция не найдена», а с загадочным:

```
Не удается привязать параметр "Id". Не удается преобразовать значение "<ТВОЙ АРГУМЕНТ>"
в тип "System.Int64". Ошибка: "Входная строка имела неверный формат."
```

**Причина.** `H` — встроенный алиас `Get-History`. Своя `function H($p){...}` его НЕ перекрывает
в том порядке разрешения имён, который тут срабатывает, и вызов уходит в командлет истории.
Тот ждёт числовой `Id` и жалуется на твой аргумент.

🔴 **Цена ошибки — не только время.** 06.08 через эту граблю в текст ошибки попало значение
токена ККТ ГИС МТ: функция сравнения хешей называлась `H`, токен ушёл в `Get-History -Id` и был
напечатан в сообщении об ошибке. То есть однобуквенное имя функции способно **выплюнуть секрет в
лог**. В ту же ночь грабля сработала дважды: сначала на сверке версий приложения (просто потеря
времени), потом на сравнении токенов (утечка).

**Правило.** В PowerShell своим функциям давать имена **минимум из трёх букв и осмысленные**:
`Hsh`, `FInfo`, `Get-FileHash12`. Однобуквенные заняты алиасами — `H`=Get-History,
`R`=Invoke-History, `%`=ForEach-Object, `?`=Where-Object, `S`/`SC`/`GC` и прочие.

**Проверка перед запуском:** `Get-Alias <имя>` — если что-то вернулось, имя занято, переименовать.

**Отдельно про секреты:** если функция работает со значением, которое нельзя печатать (токен,
пароль, полный код маркировки), нельзя полагаться на то, что оно «просто не выводится». Любая
ошибка в цепочке может напечатать аргумент. Хешировать сразу на входе и дальше носить только хеш.

## `gui-coords-native-pixels` — координаты клика считать в НАТИВНЫХ пикселях кадра (07.08.2026)

Промахнулся мимо поля ввода в окне AnyDesk и потерял на этом несколько минут в утренней аварии.
Причина простая и повторяемая, поэтому записываю.

**Что произошло.** `shot` отдаёт кадр в НАТИВНОМ разрешении экрана (обычно 1920x1080). Перед
просмотром кадр уменьшают, чтобы не жечь контекст (`convert … -resize '1400x1400>'`). Координаты,
снятые с УМЕНЬШЕННОЙ картинки, подставлять в `click` НЕЛЬЗЯ: драйвер кликает по нативным пикселям
экрана, и клик уходит левее и выше цели тем сильнее, чем крупнее элемент.

**Правило.** Координату с уменьшённого кадра умножить на `нативная_ширина / ширина_кадра`:

| ширина просмотра | множитель к нативным (при экране 1920) |
|---|---|
| 1500 | 1.28 |
| 1400 | 1.371 |
| 1200 | 1.6 |
| 1100 | 1.745 |

Пример из инцидента: поле «Enter Remote Address» на кадре шириной 1500 имело центр `(524, 183)`,
нативные — `(524×1.28, 183×1.28) = (670, 234)`. Клик по `(510, 177)` попал в пустое место, поле
осталось пустым, и это было видно только по следующему кадру.

🔴 **Проверять клик следующим кадром — обязательно.** Промах не бросает ошибку: команда отработала
успешно, просто попала не туда. Единственный признак — что на экране ничего не изменилось.

**Смежная грабля того же дня.** У ImageMagick в `-crop WxH+X+Y` смещения `+X+Y` — ВСЕГДА пиксели,
даже когда размер задан в процентах (`-crop 45%x12%+28%+48%` вырежет область 45%×12%, но от точки
(28, 48) пикселей, а не от 28% ширины). Дважды подряд получил кроп верхнего левого угла вместо
нужного участка. Считать смещения через `identify -format "%w %h"` и арифметику в шелле.

**Как правильно, коротко:**
```
W=$(identify -format "%w" кадр.jpg)          # нативная ширина
X=$((W*28/100)); Y=$((H*46/100))             # смещения в ПИКСЕЛЯХ
convert кадр.jpg -crop ${CW}x${CH}+${X}+${Y} +repage -resize 350% зум.jpg
# клик — по нативным координатам, затем ОБЯЗАТЕЛЬНО контрольный shot
```

Приоритет прежний (§27 workflow): сначала `vmatch` по эталону — он возвращает центр в нативных
координатах сам и этой ошибки не допускает; ручной пересчёт нужен только там, где эталона ещё нет.

## `1c-modal-windows` — модальные окна 1С: почему «кнопка не нажимается» и как жать её воспроизводимо (T247, 12.08.2026)

Две задачи подряд встали на ОДНОМ месте. T232 §4.1: не удалось нажать «Да» в вопросе 1С
«Предварительно необходимо рассчитать скидки (наценки). Выполнить расчет?» — перепробованы клик по
координатам из OCR (три позиции), клик по якорю от соседнего слова, `Enter` после фокуса на тексте,
`Left`+`Enter`. T246 §8: по той же причине не снят сценарий кадрами. Человек рядом жмёт эту кнопку
мышью за секунду.

Разбор на живой форме РМК копии показал **три разные причины**, и все три раньше выглядели
одинаково — «клик не доходит».

### Причина 1. Вердикт врал: «занята» принимали за «не дошёл»

Нажатие кнопки в 1С почти всегда запускает **синхронный серверный вызов**. Пока он идёт, главный
поток страницы стоит и `Runtime.evaluate` не выполняется ВООБЩЕ. Наивная проверка «а закрылось ли
окно?» получает таймаут и печатает «клик НЕ дошёл».

Замерено 12.08: клик xdotool по «OK» в диалоге штрихкода **дошёл** (товар оказался в чеке), а
драйвер в ту же секунду отрапортовал, что не дошёл. Оператор после такого рапорта идёт пробовать
ещё три способа и жмёт `Escape`, который в РМК сбрасывает уже посчитанную скидку.

Лечение (`lib/modal1c.py: probe_scan/wait_verdict`): свой сокет на каждую пробу, короткий таймаут,
и **три исхода вместо двух** — «окно ушло» / «страница ЗАНЯТА (значит клик дошёл, ждём)» /
«окно на месте и страница отвечает — вот теперь не дошёл».

### 🔴 Следствие для КАДРОВ: снимать только после закрытия окна, иначе кадр врёт (T248, 13.08.2026)

Тот же механизм («клик дошёл, но 1С ещё занята серверным вызовом») портит не только вердикт, но и
ДОКАЗАТЕЛЬСТВО. Замер 13.08: сценарий нажал «OK» в диалоге штрихкода, подождал фиксированные 12 с
и снял кадр — на кадре открытое окно «Введите штрихкод» и пустая таблица; ещё через 5 секунд в той
же форме уже стояло «Скидка: 3,00». Независимое прочтение кадра честно ответило «таблица пуста» —
и было ПРАВО: кадр показывал состояние на пять секунд раньше правды.

Фиксированный `sleep` тут не помогает: время серверного вызова 1С не постоянно. Ждать надо
СОСТОЯНИЕ, а не время:

```bash
# ГОТОВО = модальной подложки на экране нет
rc.sh modal --json            # или прямо из страницы:
# (function(){var m=document.querySelector('#modalSurface');
#   return (m && m.offsetParent!==null) ? 'ЗАНЯТО' : 'ГОТОВО';})()
```

Приём: `ждать_экран` крутит эту проверку с шагом 2 с (потолок ~80 с), и только потом `rc.sh shot`.
Правило простое: **кадр снимается по состоянию, а не по таймеру**; кадр без такой синхронизации
может опровергнуть работающую функциональность.

### Причина 2. Окно осталось, но ИЗМЕНИЛОСЬ — это тоже успех

1С не закрывает окно, когда действие отбито проверкой: она дописывает в него сообщение
(«Карта со штрихкодом … не зарегистрирована»). Первая версия вердикта считала это «не дошёл».
Теперь сравнивается и ТЕКСТ окна.

### Причина 3. 🔴 Кнопка перекрыта панелью «Сообщения» — координаты верные, клик уходит в чужой элемент

Самое неочевидное. У кнопки «Готово» мастера «Считать карту лояльности» прямоугольник
`[956,590,71x27]`, центр `(992,604)` — а `document.elementFromPoint(992,604)` возвращает
`div.messagesHeader`: панель «Сообщения:», которую 1С открывает снизу окна, ЛОЖИТСЯ ПОВЕРХ
командной панели. Клик по центру кнопки — хоть CDP-событием, хоть настоящим указателем — попадает
в панель сообщений. Снаружи неотличимо от «кнопка мёртвая», и никакой перебор способов нажатия не
помогает: перебирать надо не способ, а ТОЧКУ.

Лечение: hit-тест перед кликом (`hitPoint` в `JS_SCAN`) — проверяем `elementFromPoint`, и если
центр перекрыт, ищем свободную точку внутри самого прямоугольника кнопки (сетка 5×5). Если
свободной точки нет вовсе — драйвер это ГОВОРИТ и называет перекрывающий элемент, а не кликает
вслепую. Запасной вход в этом случае — **горячая клавиша самой кнопки**: 1С носит её в подписи
двойника из меню «Еще» (`ГотовоCtrl+Enter`), драйвер её оттуда и берёт.

### Как опознать модальное окно 1С (веб-клиент), без картинки и OCR

| Признак | Что значит |
|---|---|
| `#modalSurface.surfaceBlack`, z-index 9000, видима | экран модально заблокирован |
| `div[id$="win"].cloud` | окно платформы; верхнее — с наибольшим z-index |
| `ps0win`, `ps1win`, … (z ≈ 9004) | простой вопрос / поле ввода поверх подложки |
| `VW_page2ps0win`, … (z ≈ 1004) | форма, открытая внутри вкладки (мастер, помощник, меню РМК) |
| префикс `form<N>_` у элементов внутри | адрес элемента из метаданных формы: `form3_OK`, `form2_ОплатитьНаличными` |

🔴 Селектор `div[id^=ps][id$=win]` (первая версия) вид `VW_page2ps0win` НЕ находит: окно на экране
есть, разведка отвечает «модального окна нет». Ловить по ХВОСТУ id + классу `cloud`.

🔴 Подпись кнопки — **текстовый узел рядом с элементом-соседом** (подсказка горячей клавиши).
Поэтому обход «элементы без детей с нужным текстом» кнопку не находит вовсе (`find «Штрихкод»`
возвращал пустой список при слове на экране), а у самого текстового узла rect = 0×0 — кликать надо
предка `.pressBox`. Собирать кнопки надо по классу `press`, а не по тексту.

### Команды

```
rc.sh modal [--json]                  что за окно, кнопки (DOM и ЭКРАН), поля, точка фокуса
rc.sh modal-click <подпись> [--via x] нажать с проверкой; --via x = настоящий указатель
rc.sh modal-click --tmpl <эталон>     ТОНКИЙ КЛИЕНТ: по картинке, без CDP
rc.sh modal-fill <текст>              ввод в поле окна (Ctrl+A перед набором)
rc.sh modal-key <Enter|Escape|…>      клавиша в окно
env: RC_CDP_PORT (порт отладки браузера), RC_DISPLAY (X-дисплей для --via x)
```

Проверено вживую на ПЯТИ разных окнах РМК копии: диалог «Штрихкод» (OK/Отмена), помощник «Товар по
штрихкоду не найден» (Перенести в документ/Отмена), предупреждение «Товар не будет перенесен…»
(OK/Отмена), вопрос «Данные чека ККМ были изменены» (четыре кнопки), мастер «Считать карту
лояльности» (Готово/Отмена). Оба пути — CDP и настоящий указатель xdotool — доводят до
подтверждённого результата.

### 🔴 Веб-клиент и тонкий клиент — РАЗНЫЕ случаи

* **Веб-клиент**: окно 1С — это DOM. Есть CDP → точные координаты, подписи, hit-тест и вердикт по
  состоянию окна. Токенов на зрение ноль, картинка не нужна.
* **Тонкий клиент** (`1cv8c.exe` через RustDesk/AnyDesk): DOM нет, заглянуть внутрь нечем. Остаётся
  только картинка: эталон из `templates/` + template-match + клик в НАТИВНЫХ пикселях + контрольный
  кадр (`modal-click --tmpl`). Эталоны тонкого клиента надо резать с кадров ТОГО ЖЕ клиента —
  эталон из браузера не совпадёт (другой движок отрисовки, другие шрифты).

Эталоны веб-клиента: `templates/1c_web_modal_ok.png`, `templates/1c_web_modal_otmena.png`.

### Смежное: клавиатура в окне 1С требует РЕАЛЬНОГО клика в это окно

`Escape` в меню «Прочие операции» РМК не срабатывал ни через CDP, ни через xdotool — пока в окно не
кликнули по-настоящему. После клика в свободную точку окна (её считает `modal --json` →
`focus_point`) та же клавиша закрывает окно сразу. Это то же полевое открытие 1 (фокус клавиатуры),
только внутри страницы, а не на уровне окна вьювера.

### Привязка DOM ↔ экран (для `--via x`)

`экранный пиксель = rect + (screenX, screenY + (outerHeight − innerHeight))` при
`devicePixelRatio = 1`; смещение считает сам `modal --json` (`screen_offset`). Проверять его
надо НЕЗАВИСИМО, иначе проверка кольцевая: снять кадр страницы через CDP (`Page.captureScreenshot`,
только контент) и найти его в кадре ВСЕГО экрана template-матчем — совпадение и даёт смещение.
Замер 12.08: полоса контента, вырезанная по DOM `(500,0)`, нашлась на экране в `(500,87)` со
score 0.99 при `outerHeight − innerHeight = 87`.

🔴 Браузер для такой работы поднимать БЕЗ `Emulation.setDeviceMetricsOverride`: подмена размеров
заставляет рендерер верстать под заданный размер, картинка в окно попадает отмасштабированной, и
координаты из DOM перестают совпадать с пикселями экрана (`t211_web.py`: `T211_W=0` отключает).
