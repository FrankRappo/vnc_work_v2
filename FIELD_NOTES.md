# vnc_work_v2 — полевые заметки (обкатка вживую 2026-07-16)

Проверено на живой AnyDesk-сессии к удалённой Windows-машине. Итог: три механизма v2 рабочие,
плюс два НЕ-очевидных полевых открытия (фокус клавиатуры и калибровка haiku) и один баг-фикс.

## Три механизма (все проверены вживую)
1. **template-match** (`rc.sh find` / `click-template`, движок `vmatch.py`) — детерминированно,
   БЕЗ LLM, токенов на «зрение» НОЛЬ. Даёт точный центр эталона + score; ниже порога — репорт
   промаха, а не дикий клик. Для повторяющихся элементов (Пуск, диалоги) — основной путь.
   Вживую: Пуск найден score 1.0 в (161,1037), клик открыл меню.
2. **haiku-глаз (откалиброван)** (`rc.sh crop --grid` + haiku + `deproject`) — для НОВЫХ элементов
   без эталона. После калибровки (ниже) даёт ±1px.
3. **verify-after-click + retry** (`vmatch verify`) — сравнивает регион до/после; `changed:false`
   = клик не дошёл → re-locate + retry. Вживую ловил недошедший клик (AnyDesk иногда глотает).

## Полевое открытие 1 — КЛАВИАТУРА требует РЕАЛЬНОГО КЛИКА для фокуса (критично)
Симптом: клики по удалённой долетают, а клавиатура (`xdotool type/key`) — НЕТ (Win-клавиша не
открывала Пуск, ввод в поля не появлялся). Казалось «AnyDesk не отдаёт клавиатуру».
Причина: окну AnyDesk-сессии на :99 нужен РЕАЛЬНЫЙ КЛИК для клавиатурного фокуса.
`xdotool windowactivate <wid>` фокус ВВОДА не даёт (fluxbox) — клавиши уходят в никуда.
Фикс: ПЕРЕД любой печатью сделать реальный клик В ОКНО сессии (клик по цели через
template-match заодно и фокусит). После этого `xdotool type`/`key`/`super`/`ctrl+v` долетают.
Проверено: после клика-фокуса `xdotool key super` открыл Пуск на удалённой.
Вывод для драйвера: **клик (template) → окно в фокусе → печать**. Не полагаться на windowactivate.

## Полевое открытие 2 — КАЛИБРОВКА haiku-глаза
Симптом: на ШИРОКОМ кропе (весь низ экрана, ~20 линий сетки) haiku называл координату мимо
на сотни px (Пуск на ~160 читал как 500 — брал не ту линию).
Калибровка (что починило):
- УЗКИЙ кроп вокруг ожидаемой цели (мало линий = нельзя спутать), НЕ широкий;
- МЕЛКАЯ сетка (`--step 25`) + подписи с чёрной халообводкой (читаемы на любом фоне) —
  сделано в `stamp_grid` (veye.py): подписи сверху И снизу линий, обводка halo;
- промпт: «между какими двумя ПОДПИСАННЫМИ линиями центр» — haiku читает значение ПО ЛИНЕЙКЕ.
Результат: haiku прочитал Пуск (162,1037) при истине (161,1037) — ±1px (было мимо на 340px).
Остаточные ±1-2px = глазомерная интерполяция между линиями; для клика (кнопка ~30px) не важно.
Нужен пиксель-в-пиксель — бери template-match.

Рецепт вызова (пример):
```
python3 lib/veye.py crop --scene <кадр> --out screens/cal --region <x,y,w,h> --scale 6 --step 25 --grid --json
# → haiku читает screens/cal.png, называет real X,Y по подписям; deproject не нужен (подписи=реальные px)
```

## Полевое открытие 3 — КИРИЛЛИЦА вводится ТОЛЬКО через БУФЕР ОБМЕНА, не keystroke (T48, 2026-07-23)
Симптом (стопор T47): `xdotool type` кириллицы через RustDesk-вьювер = 1 символ/мусор — вьювер
шлёт keysym'ы/keycodes, которые раскладка удалённой Windows не мапит. Русский текст не доходит.
Фикс (проверен вживую против DESKTOP-VGVHEOU, 1С-сервер, через RustDesk):
  1. поставить ЛОКАЛЬНЫЙ X-буфер: `printf '%s' "$T" | xclip -selection clipboard` — полный UTF-8 цел;
  2. дать вьюверу СИНХРонизировать буфер на удалёнку (нужен КЛИК-фокус в окно вьювера + пауза ~0.7с);
  3. `xdotool key ctrl+v` — обычный ASCII-хоткей, вьювер его форвардит верно.
Доказано: 55-символьная кириллица («Проверка_Кириллица…_ЖилетСигнальный») вставилась ЦЕЛИКОМ в
удалённое поле, без мойбейка (readback haiku по кропу; OCR-огрехи ≠ ошибки вставки).
Инструмент: **`clip_paste.sh`** (DRY-RUN без `RC_LIVE=1`): авто-поиск окна вьювера (по площади —
крупнейшее из «Remote Desktop|RustDesk|AnyDesk»; `xdotool --name` НЕ умеет `|`-альтернацию с
пробелами → перебираем паттерны), клик-фокус в целевое поле, set-clip, пауза-синк, Ctrl+V.
Флаги: `--replace` (Ctrl+A до вставки = перезапись поля), `--enter`, `--set-only`.
Гоча: перед вводом в поле — РЕАЛЬНЫЙ клик по полю (даёт и фокус клавы, и фокус поля).

## Полевое открытие 4 — «classify: live» НЕ доказывает живую сессию (T67, 2026-07-24)
Симптом: `rc.sh classify` → `live`, кадр осмысленный (окно 1С удалённой машины) — но на экране НИЧЕГО
не менялось: запущенный на удалённой машине браузер в кадре так и не появился. Вывод «Chrome не
открылся» был бы ЛОЖНЫМ.
Причина: RustDesk-вьювер отвалился и оставил на `:99` **замороженный последний кадр** плюс свой
модальный диалог «Connection error / Closed manually by the peer». `classify` меряет только
содержательность картинки (mean/sd) — застывший кадр по этой метрике неотличим от живого.
Детектор (0 токенов, без картинки): рядом с окном сессии `«<id>@<host> - Remote Desktop - RustDesk»`
появляется отдельное top-level окно с голым именем `RustDesk` — это и есть диалог обрыва.
Сделано: **`rc.sh livecheck`** → `{"session_window":true,"viewer_dialog":1,"stale":true}`, exit 1 при
залипании. Проверено на живом обрыве. **Перед любым GUI-выводом сначала `livecheck`, потом `classify`.**

## Полевое открытие 5 — скриншот УДАЛЁННОЙ машины лучше снимать НА НЕЙ САМОЙ (T67)
`srvshot/srvshot.sh` — снимок экрана через SSH средствами самой машины (.NET `CopyFromScreen`),
без вьювера вообще. Плюсы: не зависит от живости RustDesk (см. открытие 4), нет хрома вьювера в
кадре, картинка всегда «сейчас», масштаб 1:1 (haiku читает текст точнее).
🔴 Гоча: процесс из SSH живёт в **сессии 0** и снимет ЧЁРНЫЙ кадр. Запускать только через
`schtasks /ru <user> /it` (интерактивный токен, сессия 1) — так сделано в `shot_run.ps1`.
Гоча-2: сам bat-лаунчер показывает окно `cmd.exe` ПОВЕРХ цели и портит кадр. Нужное окно поднимать
на передний план программно (`EnumWindows` + `SetForegroundWindow` по подстроке заголовка), затем
снимать; заголовки окон заодно бесплатно отвечают «а открылось ли вообще».

## Полевое открытие 6 — JS-антибот: curl видит заглушку, настоящий браузер — сайт (T67)
`atol.ru` / `fs.atol.ru` отдают `curl`/`Invoke-WebRequest` ~13.6 КБ JS-заглушку (ровно **13602**
байта) — и с RU-IP, и с браузерным UA. Вывод «файлов нет», сделанный по curl, недостоверен.
Решение — `cdp/` (см. `cdp/README.md`): headless Chrome с портом отладки на удалённой машине,
страницы возвращаются ТЕКСТОМ через CDP. Cookie из этого браузера (`__js_p_`, `__jhash_`, `__jua_`)
+ ЕГО ЖЕ User-Agent, отданные `curl.exe`, открывают и прямое скачивание файлов.

## Полевое открытие 7 — кабинет (Vaadin/SPA) водится ДОВЕРЕННЫМ вводом, а данные брать из СЕТИ (T71, 2026-07-25)
Задача: достать из ЛК ОФД карточку конкретного чека (марочная позиция, ошибки ФД). Прошли три
ложных вывода подряд — каждый чинится одним механизмом:
1. «Клик по строке грида не доходит» — на самом деле `el.click()` (untrusted) грид игнорирует.
   Фикс: `CDP_CLICK="x,y"` → `Input.dispatchMouseEvent` (см. `cdp/README.md` гоча 8).
   Проверка попадания без картинки: `document.elementFromPoint(x,y)` + `grid.activeItem`.
2. «Двойной клик не работает» — одно событие с `clickCount:2` не даёт `dblclick`; нужны ДВЕ пары
   press/release (1, затем 2). Карточка ЛК ОФД-Я открывается именно по ДВОЙНОМУ клику.
3. «Ничего не открылось» — модалка была `<iframe>`, а `document.body.innerText` содержимое
   iframe НЕ включает. Дамп `outerHTML` + греп показал `<iframe src="VAADIN/dynamic/resource/...">`.
   Читать: `CDP_FRAME=<подстрока URL>` (Runtime.evaluate в main world фрейма — видны его
   JS-переменные `ext_json`/`cname`, т.е. РАЗОБРАННЫЙ сервером документ, а не вёрстка).
Плюс `cdpnet.sh` (CDP Network domain): показывает, ЧТО сервер ответил на действие. Пустой UIDL
(`for(;;);[{"syncId":N,"clientId":N}]` без `execute`) = «клик дошёл, делать нечего» — это отличает
недошедший клик от отключённого пункта меню (у нас так вскрылось, что раздел «Уведомления о КМ»
у аккаунта `disabled`, а не «не кликается»).
Экономика: ноль скриншотов и ноль токенов на зрение — весь разбор по тексту/JSON.

## Полевое открытие 8 — вход в кабинет по ЭЦП делается ПОДПИСЬЮ, а не браузерным плагином (T72, 2026-07-25)
Задача: попасть в ЛК Честного знака (вход только «Войти с электронной подписью») и прочитать карточку
выбытия кода. Плагин `КриптоПро ЭЦП Browser plug-in` живёт в ПРОФИЛЕ владельца, а его Chrome запущен
(профиль под эксклюзивной блокировкой) — казалось, что без владельца никак. Оказалось, плагин не нужен.

**Вход = один HTTP-раунд с подписью, из PowerShell:**
```
GET  /api/v3/auth/cert/key                 -> {uuid, data}          (или /api/v3/true-api/auth/key)
     подписать data
POST /api/v3/auth/cert/  {uuid, data:<b64>} -> {token}   (True API: /api/v3/true-api/auth/simpleSignIn)
```
🔴 Гоча, которая стоила 4 круга: подпись должна быть **ПРИСОЕДИНЁННАЯ (attached)** над UTF-8-байтами
строки `data`. Открепленная (как читается в методичках) отвергается: `403 {"error_message":"Подпись
невалидна. Код ошибки: 2"}`. Матрица, которую пришлось прогнать (все detached → 403): UTF-8, UTF-16LE,
base64(data), hex-decoded. Прошла только attached/UTF-8.
Подписывать — штатным .NET, CryptoPro CSP подхватывается через CAPI:
`SignedCms(ContentInfo, detached=false)` + `CmsSigner(cert)` с `DigestAlgorithm = 1.2.643.7.1.1.2.2`
(ГОСТ Р 34.11-2012 256), `ComputeSignature($signer, $true)` — **silent=true работает, PIN не спрашивается**;
`signingCertificateV2` (1.2.840.113549.1.9.16.2.47) .NET добавляет сам, т.е. это уже CAdES-BES.
`CAdESCOM.Store.Open(...)` из PowerShell падает `NullReferenceException` (COM-биндер) — в CAdESCOM лезть
не нужно вообще.

**Архитектура кабинета ЦРПТ (важно для навигации):** `markirovka.crpt.ru` = ЕЛК-оболочка;
данные по товарной группе — на ОТДЕЛЬНОМ хосте `<группа>.crpt.ru` (вода → `water.crpt.ru`).
Токен = СЫРОЙ JWT в `localStorage['token']`; между поддоменами шарится КУКАМИ на `domain=.crpt.ru`:
`count`, `tokenPart<N>` (нарезка по 4000 симв.), `tokenType=Bearer`, `tokenStorageLocation=cookie`.
Выставить их из JS + положить `localStorage['token']` = полноценный вход в кабинет группы (проверено:
шапка «ЧЕПРАСОВ В. В.», меню Коды/Склад/Документы/Чеки).
- 🔴 `/api/v3/facade/*` отдаёт `403 nginx` ВСЕМ и ВСЕГДА (и из PowerShell, и из same-origin fetch
  настоящего браузера, и с токеном, и с куками) — мёртвый префикс из старого бандла. Не тратить круги.
  Живой API кабинета — `/bff-elk/...`, и он спокойно принимает `Authorization: Bearer` из ЛЮБОГО клиента.
  То есть: браузер нужен ровно чтобы УЗНАТЬ имена ручек (`cdpnet.sh`), дальше — обычный HTTP.
- Роуты у кабинетов РАЗНЫЕ: у воды Документы = `/requests/list` (а не `/documents/list` — тот даёт
  «СТРАНИЦА НЕ НАЙДЕНА»), Чеки = `/receipt/list`, Коды = `/cis/list`.
- Фильтр `POST /bff-elk/v1/cis-history/list` требует `{"cis":["<КИ>"]}` — СПИСОК. Строкой →
  `400 Failed to read HTTP message`, а вложенным `{"filter":{"cis":...}}` → `400 «Должен быть заполнен
  параметр cis»`. Два разных 400 на одну ошибку — не путать.
- Выбытие через ККТ — НЕ документ: в `doc/list` / «Документы» его нет вообще, он лежит в реестре
  «Чеки» (`POST /bff-elk/v2/receipts/search`) как «Чек на реализацию», а история кода ссылается на него
  по `docId`. Искать его среди документов = гарантированный ложный вывод «документа нет».

## Инструмент: `rps.sh` / `rps_run.ps1` — PowerShell на удалённой машине с UTF-8 наверх (T72)
`bash rps.sh probe.ps1 /tmp/out.txt` — залить скрипт, выполнить, забрать вывод ТЕКСТОМ в UTF-8.
Зачем отдельный хелпер, а не `ofd_ssh.sh 'powershell -Command ...'`:
1. stdout OpenSSH идёт через кодовую страницу консоли (cp866) → кириллица в мойбейк, гpepы мимо;
2. командную строку ssh СНАЧАЛА разбирает `cmd.exe`, поэтому `*>&1` в `-Command` съедается как
   cmd-редирект (получаешь синтаксическую ошибку PowerShell и отлаживаешь не то);
3. PS 5.1 читает файл без BOM как ANSI → кириллические литералы в скрипте ломаются (rps.sh дописывает BOM).
Раннер стримит вывод (`Out-String -Stream`) — то, что напечаталось ДО падающей строки, доходит
(буферизация через один `Out-String` теряла всё и проба читалась как «ничего не работает»).

## Гочи PowerShell, которые стоили кругов (T72)
1. 🔴 **Имена переменных в PowerShell РЕГИСТРОНЕЗАВИСИМЫ.** `$h` и `$H`, `$b` и `$B` — ОДНА переменная.
   `$H='https://…'` затем `$h = ... | ConvertFrom-Json` молча убивает базовый URL, и получаешь
   `Недопустимый URI: Невозможно определить формат URI` в месте, где всё «очевидно правильно».
2. `Try` — зарезервированное слово: функция с таким именем даёт «В операторе Try отсутствует блок операторов».
3. `МояФункция ... | Out-Null` глотает и печать функции тоже → файл вывода на 0 байт («ничего не вернулось»).
4. Per-object `$_ | Out-String` в конвейере после `Format-Table` падает `NullReferenceException`
   (Format-Table подмешивает null-элементы) — использовать `Out-String -Stream` на весь поток.
5. 🔴 **Маскировать секреты ДО обрезки.** `substring(0,200)` обрубает `"token":"…"` и regex-маска
   перестаёт совпадать → в лог уезжает начало живого JWT. Сначала mask, потом truncate.
