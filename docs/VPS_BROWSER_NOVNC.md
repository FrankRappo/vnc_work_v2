# Браузер VPS в браузере Windows: noVNC и сохранённая сессия

Проверено 24.10.2026: владелец открыл ссылку в Windows и сам завершил вход
в уже работающем браузере VPS. Затем он вернул управление агенту.
Отдельная VNC-программа на Windows для этого не нужна.

## Как устроено подключение

```text
Браузер Windows: http://127.0.0.1:6087/vnc.html
    → localhost-переадресация Windows/WSL
    → SSH-туннель WSL 127.0.0.1:6087 → VPS 127.0.0.1:6087
    → websockify + noVNC на VPS
    → x11vnc на VPS 127.0.0.1:5907
    → существующий дисплей :97 с тем же Chromium и профилем
```

noVNC отдаёт страницу и подключается через WebSocket к websockify; тот передаёт
VNC-протокол x11vnc. Человек видит экран существующего браузера и управляет его
мышью и клавиатурой. Агент после возврата управления использует тот же браузер
через framework/CDP. Локальный Chromium с новой сессией не запускается.

| Компонент | Где работает | Пример адреса |
| --- | --- | --- |
| Chromium, профиль, Xvfb/Xauthority | VPS, пользователь браузера | дисплей `:97`, CDP `127.0.0.1:9347` |
| x11vnc | VPS, тот же пользователь | `127.0.0.1:5907` |
| noVNC + websockify | VPS | `127.0.0.1:6087` |
| SSH-туннель | WSL, разрешённый транспорт проекта | локальный `127.0.0.1:6087` |
| Окно пользователя | Windows | ссылка noVNC на localhost |

Номера портов и дисплея — пример рабочего подключения, а не глобальные значения.
Перед запуском проверяйте занятость, владельца процессов и соответствие профиля.
Запишите VPS, пользователя, удалённые пути приложения/профиля/артефактов и способ
доступа в закрытый журнал задачи. Не используйте секреты и данные кабинета в Git.

## 1. Подключить существующий дисплей на VPS

Сначала найдите фактически работающий браузер, его дисплей, Xauthority, CDP и
профиль. Не запускайте второй браузер и не меняйте чужие вкладки/дисплеи.
При отсутствии разрешённого доступа восстановите штатный транспорт проекта;
локальный стенд или обходной SSH не заменяют VPS.

На AlmaLinux 9 в проверенном подключении понадобились пакеты `x11vnc`, `novnc`
и `python3-websockify`. Установка выполнялась **на VPS** через разрешённый
административный канал. Если пакеты уже установлены, повторная установка не нужна.
Статические файлы noVNC находились в `/usr/share/novnc`.

Следующие команды выполняются **на VPS от пользователя существующего браузера**.
Замените пути фактическими путями задачи и убедитесь, что порты свободны.
Если слушатель уже существует, проверьте и используйте его вместо второго запуска.

```bash
TASK_ROOT='/path/to/owned/private/browser-task'
TASK_DISPLAY=':97'
TASK_XAUTHORITY="$TASK_ROOT/Xauthority"
umask 077
test -d "$TASK_ROOT"
test -r "$TASK_XAUTHORITY"
ss -ltnp

nohup /usr/bin/x11vnc \
  -display "$TASK_DISPLAY" -auth "$TASK_XAUTHORITY" \
  -rfbport 5907 -localhost -noipv6 -forever -shared \
  -nopw -noxdamage -nolookup -q \
  >"$TASK_ROOT/x11vnc.private.log" 2>&1 </dev/null &
printf '%s\n' "$!" >"$TASK_ROOT/x11vnc.pid"

nohup /usr/bin/websockify --web /usr/share/novnc \
  127.0.0.1:6087 127.0.0.1:5907 \
  >"$TASK_ROOT/novnc.private.log" 2>&1 </dev/null &
printf '%s\n' "$!" >"$TASK_ROOT/novnc.pid"
```

`-nopw` здесь относится только к изолированным loopback-слушателям за SSH на
доверенной машине владельца. Если такой границы доступа нет, настройте частную
VNC-аутентификацию; не открывайте этот вариант на публичном интерфейсе.
Порт CDP также остаётся на loopback и не публикуется.

В проверенной версии x11vnc опция `-silent` не поддерживалась; использован `-q`.
Каталог профиля/закрытых артефактов имеет права `0700`, закрытые файлы — `0600`.
PID-файл сам по себе не доказывает готовность: проверьте процесс, дисплей и сокет.

## 2. Прокинуть noVNC через штатный SSH

В рабочем случае использован уже открытый, проверенный SSH ControlMaster проекта.
Дополнительный туннель сохранил его маршрут и не потребовал новой аутентификации.
Никакие публичные порты VPS, firewall или настройки маршрутизации не менялись.

Если workflow разрешает переиспользовать существующий master для forwarding,
выполните в WSL следующий шаблон с **фактическими параметрами штатного канала**.
При наличии собственного forwarding-helper проекта используйте его.

```bash
TASK_MUX_SOCKET='/path/to/approved/control/socket'
TASK_SSH_TARGET='APPROVED_USER@APPROVED_VPS'
TASK_SSH_PORT='APPROVED_SSH_PORT'

ssh -S "$TASK_MUX_SOCKET" -p "$TASK_SSH_PORT" \
  -O check "$TASK_SSH_TARGET"

tmux new-session -d -s owned_browser_novnc_tunnel \
  /usr/bin/ssh -S "$TASK_MUX_SOCKET" -p "$TASK_SSH_PORT" \
  -o ControlMaster=no -o BatchMode=yes -o StrictHostKeyChecking=yes \
  -o ProxyCommand=/bin/false -o ExitOnForwardFailure=yes \
  -N -L 127.0.0.1:6087:127.0.0.1:6087 "$TASK_SSH_TARGET"
```

Проверьте идентичность master по журналу транспорта, а не только наличие файла
сокета. `ProxyCommand=/bin/false` в этом шаблоне предотвращает незаметный переход
к новому прямому соединению при потере master. Не перезапускайте общий master
и не меняйте путь/ключ/маршрут, чтобы заставить пример заработать.
Туннель должен жить после завершения команды агента; здесь его удерживает tmux.

## 3. Проверить путь именно из Windows и открыть ссылку

Проверка по слоям:

1. На VPS x11vnc связан с нужным дисплеем и слушает loopback `5907`;
   websockify слушает loopback `6087` и направлен на этот x11vnc.
2. Через туннель `/vnc.html` отвечает HTTP `200` со страницей noVNC.
3. `/websockify` выполняет WebSocket upgrade `101 Switching Protocols`
   с subprotocol `binary`; первый бинарный кадр содержит `RFB 003.008`.
4. Windows тоже получает HTTP `200`, а в браузере виден нужный рабочий стол.

Один HTTP `200` не подтверждает рабочее изображение/управление: WebSocket может
не подключиться к VNC. Один PID не подтверждает ни HTTP, ни VNC.

Команды **в PowerShell Windows**:

```powershell
$TaskVncUrl = 'http://127.0.0.1:6087/vnc.html?autoconnect=1&resize=scale'
$TaskVncResponse = Invoke-WebRequest -UseBasicParsing -TimeoutSec 10 -Uri $TaskVncUrl
$TaskVncResponse.StatusCode
Start-Process $TaskVncUrl
```

В подтверждённом подключении проверены HTTP `200`, WebSocket `101/binary`,
баннер `RFB 003.008`; затем владелец подтвердил успешный ручной вход.
Переадресация localhost между Windows и WSL сработала в этой среде; после её
перезапуска это нужно проверить снова. Если работает только WSL, ещё нельзя
выдавать ссылку как готовую для Windows. Не заменяйте loopback публичным bind
и не отключайте firewall; восстановите разрешённый клиентский канал.

Ссылка для пользователя: **http://127.0.0.1:6087/vnc.html?autoconnect=1&resize=scale**.
Откройте её в обычном браузере Windows. Внутри страницы находится VNC с браузером
VPS — данные вводятся именно в этот удалённый экран. Ссылка работает на машине
с туннелем; это не общедоступная ссылка на кабинет.

## 4. Передавать управление и сохранять сессию

1. Агент открывает нужную страницу, проверяет настоящий экран и готовит ссылку.
2. Перед ручным вводом сообщает `WAITING_OWNER_2FA` или `OWNER_MANUAL_CONTROL`.
   Останавливает клики, ввод, навигацию и снимки экрана на время ввода человеком.
3. Человек завершает вход и явно возвращает управление: «зашёл, продолжай».
4. Агент заново проверяет текущие вкладки и признак авторизации. Человек мог
   открыть другую вкладку; старый target ID/URL не доказывает текущее состояние.
5. Агент сохраняет тот же закрытый профиль на VPS, оставляет браузер/дисплей/
   VNC/туннель живыми и продолжает в этой сессии. Не выполняет обычный `down`,
   удаление профиля или logout, если владелец попросил сохранить доступ.

В журнале достаточно статуса авторизации, приватных путей, владельца/прав,
дисплея, портов, идентичности процессов и результата подключения. Пароли, OTP,
cookie, токены, OAuth-параметры и содержимое кабинета в Git/отчёты не попадают.
При необходимости сохранения состояния авторизации используйте закрытый
артефакт на VPS, доступный только владельцу браузера, и не выводите его значения.
Не архивируйте активные SQLite-файлы профиля как будто это согласованный бэкап.
Истечение банковской сессии/OTP определяется банком; сохранённый профиль
не гарантирует бессрочный вход.

## Если внутри VNC видна ошибка входа

Работающий VNC может показывать старую `/auth/error?...error=invalid_request`:
это состояние вкладки, а не адрес VNC. Не давайте человеку ссылку на этот старый
OAuth `cid` как начало входа. После согласованной передачи управления откройте
официальную начальную страницу сервиса в том же профиле либо дайте человеку
начать новый вход. Не перезагружайте вкладку, пока он вводит данные, и не
запускайте автоматическую повторную отправку пароля/SMS.

После работы оставляйте сохранённую сессию по указанию владельца. Если он
попросит завершить доступ, отключайте только проверенные процессы/туннели
этой задачи; общий SSH master, чужие дисплеи и другие профили сохраняются.
